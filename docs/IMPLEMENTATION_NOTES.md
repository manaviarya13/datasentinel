# Implementation notes\n\n## Package layout\n\n- `src/datasentinel/detector`: known-answer prompt construction and decision.\n- `src/datasentinel/attacker`: objective definitions, separate threat models, separator constraints, GCG candidate search, and adaptive evaluation orchestration.\n- `src/datasentinel/training`: alternating minimax orchestration, detector objective, concrete causal-LM detector update, and adapter checkpoints/logs.\n- `src/datasentinel/models`: lazy QLoRA and causal-LM loss utilities.\n- `src/datasentinel/data`: source-split preserving local records, loader, deterministic split/sample helpers, and paper task inventory.\n- `src/datasentinel/evaluation`: confusion counts and classification metrics.\n\n## Objective sign audit\n\nGCG minimizes `key_CE + alpha * backend_CE`; this equals maximizing the paper's negative weighted sum. The defender minimizes `-J1 + beta*J2`; the negative contaminated term increases key loss on attacks, while the clean term decreases key loss on clean input. Both objectives are unit-tested with hand-computed values.\n\nThe two human-crafted adaptive evaluation variants come from Section V-D1. Adaptive-I inserts its quoted separator between `x_t` and `s_e || x_e`; adaptive-II appends the quoted sentence after `s_e || x_e`. No additional boundary whitespace is stated in the paper, so the implementation uses direct concatenation and records this as an engineering assumption. These functions are evaluation-only and are not used by minimax training.\n\n## Limits\n\nModel-specific GCG gradients need a cross-model/shared-text adapter. Until this is resolved against author code or source evidence, no real minimax attacker run should be described as a faithful complete run. The generic optimizer and callbacks enforce token edit scopes but are not substitutes for a validated model adapter.\n
