# Shared-separator GCG across Mistral and LLaMA3\n\n## Finding\n\nThe DataSentinel paper specifies a single textual separator `z`, inserted as `x_c = x_t || z || s_e || x_e`, and maximizes the mean of the unchanged joint objective\n\n`J(z) = mean_pairs[-ell(k, g(s_d || x_t || z || s_e || x_e)) - alpha * ell(y_e, f(s_t || x_t || z || s_e || x_e))]`.\n\nBoth model losses contribute to the same scalar objective. The paper does not state how the gradient for the one textual `z` is computed across the Mistral detector and LLaMA3 backend tokenizers, nor does it give a token alignment or gradient projection. This remains an unspecified method detail.\n\nThe authors' released model configs identify `mistralai/Mistral-7B-v0.1` and `meta-llama/Meta-Llama-3-8B-Instruct`. Their tokenizer vocabularies have 32,000 and 128,256 entries respectively. The model cards/configs give hidden size 4,096 for each, but this equal dimension does not make their learned embedding bases or token IDs interchangeable. Adding vocabulary-gradient vectors is dimensionally invalid; projecting by token ID is semantically invalid. This project does neither.\n\n## What cited GCG does and does not establish\n\nGCG computes a loss gradient with respect to each editable one-hot token, selects top-k tokens by negative gradient, samples candidate coordinate replacements, evaluates candidates with exact forward losses, and commits the lowest-loss candidate. Its universal multi-prompt formulation aggregates clipped gradients and exact losses when one suffix is shared across prompts. That formulation motivates shared-control optimization, but does not define DataSentinel's cross-tokenizer alignment for two different model vocabularies and objectives. The upstream implementation keeps a common control string but maintains model/tokenizer-specific token controls; its parameters and constraints are versioned code defaults, not DataSentinel paper settings.\n\n## Candidate-based alternatives\n\nLet model `m` have tokenizer `tau_m`, vocabulary `V_m`, and loss `L_m(z)` (including the task-pair batch average and its paper weight: detector weight 1, backend weight `alpha`). Let `z` be the shared text. The actual objective is `J(z)=L_g(z)+L_f(z)`, with both losses recomputed from the same text using each model's own tokenizer.\n\n| Approach | Proposal rule | Selection rule | Assessment |\n|---|---|---|---|\n| Directly add gradients | Add `grad_g` and `grad_f` at matching token positions/IDs | Rank shared token IDs | Invalid: vocabularies and token meanings differ. |\n| Project gradients to a common embedding space | Learn or define `P_g`, `P_f` and add projected gradients | Shared projected top-k | Mathematically possible only after choosing and validating mappings. No such projection is in the paper or author release; it adds a learned method component. Not selected. |\n| Canonical-tokenizer proposals + joint reranking | Use one model's token gradient to propose decoded text edits; retokenize and score each candidate under both models | `argmin_{z' in C union {z}} J(z')` | Simple and valid descent candidate selection for the paper objective, but ignores the other model's gradient during proposal generation. Approximation. |\n| Independent model-local proposals, textual union + joint reranking | For each model, compute its own embedding/one-hot gradient; use that tokenizer's offsets and vocabulary to create text replacements. Deduplicate the resulting strings. | Tokenize every candidate independently with both models; exact joint forward score; commit `argmin J` | Selected engineering approximation. It respects one shared text and exact paper loss in candidate evaluation without combining incompatible gradients. It is not the paper-specified gradient rule. |\n| Character/byte search | Propose edits in a tokenizer-independent character or byte alphabet | Score all candidates with exact `J` | Valid black-box discrete search, but it is no longer the paper's GCG token proposal rule and can be much less efficient. Not selected. |\n\n## Selected engineering approximation\n\nThe code in `src/datasentinel/attacker/shared_separator.py` implements the fourth approach:\n\n1. Keep one `z` string and a separate tokenizer/gradient view per model.\n2. Tokenize the current `z` separately with each model's tokenizer and request character offsets.\n3. For each model-local editable token position, rank that model's own vocabulary IDs by the negative local loss gradient. Decode only those local token IDs with that model's tokenizer.\n4. Replace the token's character span in the shared string to create text proposals. Do not add gradients across models. Do not impose an ASCII filter; DataSentinel's reported learned separator contains non-ASCII characters.\n5. Deduplicate textual candidates. The joint scoring callback constructs complete model inputs and independently tokenizes them with each model's tokenizer. It evaluates the paper objective, `L_g + alpha L_f`, exactly for each candidate.\n6. Compare the current `z` and proposals using the joint score and commit the lowest-scoring candidate. A configured candidate budget may cap evaluation; that budget is an engineering choice and must be manifested.\n\nPseudocode:\n\n```text\nz = shared_separator_text\nrepeat paper n_in updates:\n    proposals = {}\n    for (model, tokenizer, model_loss) in [detector, backend]:\n        ids, char_offsets = tokenizer(z, offsets=True)  # independent encoding\n        grad = gradient_of(model_loss, model_local_one_hot_ids=ids)\n        for local_position in editable_separator_tokens:\n            for token_id in top_k(-grad[local_position]):\n                replacement = tokenizer.decode(token_id)\n                proposals.add(replace(z, char_offsets[local_position], replacement))\n    candidates = deduplicate(proposals)  # strings; no gradient-vector addition\n    for candidate in candidates:\n        detector_loss = score_detector(tokenizer_g(full_detector_input(candidate)))\n        backend_loss = score_backend(tokenizer_f(full_backend_input(candidate)))\n        joint_loss[candidate] = detector_loss + alpha * backend_loss\n    z = argmin({z} union candidates, joint_loss)\n```\n\nThis keeps the paper's objective and shared-separator constraint. The engineering approximation is only in how candidate strings are proposed and aligned.\n\n## Assumptions and limitations\n\n- Fast tokenizers must return character offsets for the separator. Slow tokenizers require a documented decoder-alignment adapter; do not guess offsets.\n- Replacing a token's character span can change neighboring tokenization and the number of tokens in `z`. Each full candidate is re-tokenized for both models. No fixed separator-token count is stated by the paper, so the selected implementation does not add one.\n- A decoded local token can include leading whitespace or special-token behavior. Special tokens, zero-width spans, empty decodes, duplicate strings, and candidate round-trip behavior need explicit filtering/recording in model-backed integration.\n- Candidate strings from the two models are not paired coordinate-wise. The joint exact loss determines which proposal is accepted. This can be inefficient and proposal coverage may be asymmetric.\n- Detector and backend CE losses are token-sequence sums in the paper. If lengths differ, raw sequence sums have length-dependent scale; preserving that formulation is paper-faithful, while any normalization would change the objective and must be declared separately.\n- `top_k`, proposal budget, character-span edit semantics, candidate validity filters, initialization length/distribution, and cross-step stopping are unresolved in the paper. They remain run configuration values marked engineering choices or null until sourced.\n- The minimax attacker alone uses this shared learned separator in `x_c = x_t || z || s_e || x_e`. Realistic evaluation GCG remains separate: it uses a surrogate key per step and can edit the full contaminated text. Manual adaptive-I/II variants are also separate.\n\n## Tests and implementation status\n\nDependency-free fake-tokenizer tests verify that proposal IDs are decoded by their own tokenizers, local tokenizer offsets create different text proposals, and the joint scorer receives each candidate for independent model-side tokenization. They do not validate gradients or any real Mistral/LLaMA model. A reduced-scale model run must check gradients, exact scoring, offset correctness and objective descent before calling this adapter useful.\n\n## Sources\n\n- [DataSentinel arXiv v4, equations (2), (5), Algorithms 1–2 and Section V-A](https://arxiv.org/html/2504.11358v4#S4)\n- [GCG paper, Sections 2.2–2.3, Algorithms 1–2](https://arxiv.org/html/2307.15043)\n- [GCG reference implementation: candidate generation, local tokenizers, and multi-model control handling](https://github.com/llm-attacks/llm-attacks/blob/main/llm_attacks/base/attack_manager.py)\n- [Mistral model config](https://huggingface.co/mistralai/Mistral-7B-v0.1/blob/main/config.json)\n- [Official authors' Mistral config](https://github.com/liu00222/Open-Prompt-Injection/blob/main/configs/model_configs/mistral_config.json) and [LLaMA3 config](https://github.com/liu00222/Open-Prompt-Injection/blob/main/configs/model_configs/llama3_config.json)\n
